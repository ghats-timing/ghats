\chapter{GHATS File Formats}
\label{app:file-formats}

This appendix describes the file formats written and read by the current GHATS
routines for native timing products and bispectrum products.  It is a
description of the implementation, not a new definition of the science
conventions.

The source of truth is the IDL code.  In particular, the native PDS and FFT
formats are written and read by:

\begin{itemize}
\item \routine{mu_write_single_power}
\item \routine{mu_write_single_fft}
\item \routine{mu_compute_fft}
\item \routine{ghats_getheader}
\item \routine{ghats_openpds}
\item \routine{ghats_openfft}
\item \routine{read_pds_line}
\item \routine{read_fft_line}
\end{itemize}

The dynamic-PDS FITS format is written by \routine{gh_dyn_fits}.  The
bispectrum FITS products are written and read by:

\begin{itemize}
\item \routine{gh_bispec_fits}
\item \routine{gh_write_bispec_fits}
\item \routine{gh_write_cross_bispec_fits}
\item \routine{gh_read_bispec_fits}
\end{itemize}

\section{Scope}

This appendix covers:

\begin{itemize}
\item GHATS binary \texttt{.pds} files;
\item GHATS binary \texttt{.fft} files;
\item GHATS dynamic-PDS FITS files written by \routine{gh_dyn_fits};
\item GHATS bispectrum FITS files.
\end{itemize}

It does not cover mission event files read as input, log files, PostScript
plots, screen output, text parameter files, file lists, metafiles, or
XSPEC/OGIP products such as \texttt{.pha} and \texttt{.rmf}.

\section{IDL Binary Products}

GHATS \texttt{.pds} and \texttt{.fft} files are IDL unformatted binary files
written with \param{WRITEU} and read with \param{READU}.  The files use the
native binary layout of the platform that wrote them.  Current GHATS products
are normally little-endian, but external readers should verify the header
fields rather than assuming that a product is valid.

Both formats have the same fixed header and the same per-transform metadata
record.  The final payload in each transform differs:

\begin{itemize}
\item \texttt{.pds} stores one real power array per transform;
\item \texttt{.fft} stores one complex Fourier-amplitude array per transform.
\end{itemize}

\subsection{Shared Header}

The header is written once at the beginning of the file by
\routine{mu_write_single_power} or \routine{mu_write_single_fft}.  It is read by
\routine{ghats_getheader}.

\param{version_id} & string, 16 bytes & GHATS/version identifier. \\

The number of transforms, \param{ntotal_ffts}, begins at byte offset 84 in the

and patch this field after the final number of transforms is known.

\begin{longtable}{>{\raggedright\arraybackslash}p{0.25\textwidth}>{\raggedright\arraybackslash}p{0.62\textwidth}}

\endhead

\bottomrule
\end{longtable}

Some readers also inspect later \param{dummy} bytes for mission-specific
quantities.  Those bytes should be treated as reserved unless a
product-specific writer documents them.

\subsection{Frequency Grid}

For both \texttt{.pds} and \texttt{.fft}, the stored frequency bins are
reconstructed as:

\begin{ghatsconsole}
frequency = (FINDGEN(nft / 2) + 1.0) * T
\end{ghatsconsole}

The DC bin is not stored.  The stored array contains bins 1 through
\param{nft}/2, including the Nyquist bin.

The segment duration represented by one transform is:

\begin{ghatsconsole}
duration = 1.0 / T
\end{ghatsconsole}

The time resolution of the original binned light curve is:

\begin{ghatsconsole}
dt = duration / nft
\end{ghatsconsole}

The Nyquist frequency is:

\begin{ghatsconsole}
nyquist = nft * T / 2.0
\end{ghatsconsole}

\subsection{PDS Normalization}

For normal GHATS PDS production, \routine{mu_compute_fft} computes the Fourier
transform and then writes powers as:

\begin{ghatsconsole}
pwr = ABS(rdata[1:np/2])^2 * 2.0 / cnts
\end{ghatsconsole}

Here \param{cnts} is the total number of counts in the windowed input segment.
This is Leahy normalization.

For RXTE/PCA products, the Poisson level may be computed with the Zhang et al.
prescription through \routine{mu_zhang}.  For non-PCA products, the stored
Poisson level is normally 2.0 unless the mission writer sets something else.

\section{\texttt{.fft} Files}

A \texttt{.fft} file stores the complex Fourier amplitudes for each selected
transform.

\begin{longtable}{>{\raggedright\arraybackslash}p{0.18\textwidth}>{\raggedright\arraybackslash}p{0.22\textwidth}>{\raggedright\arraybackslash}p{0.18\textwidth}>{\raggedright\arraybackslash}p{0.30\textwidth}}
\toprule
Field & IDL type & Length & Meaning \\
\midrule
\endhead
\param{rdata} & complex array & \param{nft}/2 & Complex Fourier amplitudes for frequency bins 1 through \param{nft}/2. \\
\bottomrule
\end{longtable}

IDL complex values are stored as two 32-bit floating-point numbers per element:
real part followed by imaginary part.

\subsection{FFT Convention}

The stored FFT array is produced in \routine{mu_compute_fft} as:

\begin{ghatsconsole}
rdata = FFT(rdata, 1, /OVERWRITE)
fftdata = rdata[1:np/2]
\end{ghatsconsole}

The DC bin is not stored.  GHATS therefore stores the positive-frequency bins
produced by IDL \param{FFT(input, 1)}.

The source comment in \routine{mu_compute_fft} notes that the IDL call used here
corresponds to the forward transform in the convention used by the original
GHATS timing routines.  External code that computes cross spectra or lags
should match this implementation convention rather than changing the lag sign
convention.

\subsection{FFT Units}

The \texttt{.fft} payload is the raw complex Fourier amplitude.  It is not saved
in Leahy, rms, or fractional-rms normalization.  Normalizations are applied
later by analysis routines that read the FFT products.

\section{Bispectrum FITS Files}

The current GHATS bispectrum FITS format is image-extension based and is written
by \routine{gh_bispec_fits} through \routine{gh_write_bispec_fits}.  The primary
HDU contains a dummy one-byte image.  This is intentional: it avoids problems
with FITS writers that do not handle a zero-length primary image reliably.

\subsection{Reading Bispectrum FITS Products}

\routine{gh_read_bispec_fits} reads current products primarily by
\param{EXTNAME}.  It also contains fallback behaviour for older files with less
complete extension naming.  New readers should prefer \param{EXTNAME} over
extension number wherever possible.

\section{Compatibility Notes}

The binary \texttt{.pds} and \texttt{.fft} formats are compact and historically
tied to IDL's native binary representation.  The FITS products are more
self-describing, especially the bispectrum products, where extensions are named
and frequency-axis metadata are written.

When checking compatibility between \texttt{.pds} files, routines should compare
at least:

\begin{itemize}
\item \param{nft};
\item frequency resolution \param{T};
\item transform duration \(1/T\);
\item Nyquist frequency \(\param{nft}\,\param{T}/2\);
\item channel range;
\item observatory and instrument metadata, when relevant to the analysis;
\item normalization and Poisson-handling assumptions implied by the producing
      routine.
\end{itemize}

For \texttt{.fft} files, compatibility checks should additionally ensure that
later cross-spectral or lag calculations use the same GHATS Fourier and lag
conventions.
